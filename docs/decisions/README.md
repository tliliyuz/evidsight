# 架构决策记录

本目录记录会长期影响服务边界、安全、数据生命周期、公共契约或兼容性的决策。

每份 ADR 使用状态 `proposed|accepted|superseded|deprecated`，包含背景、决策、后果、被否决方案、重新评估触发条件和相关规范。已接受 ADR 不因实现尚未完成而失效；实现偏离时必须先修订或替代 ADR。

## 创建门禁

每项新功能、Bug 修复、行为变更或架构调整必须在规格设计开始时执行 ADR 检查。设计过程中出现新的方案选择或影响范围扩大时重新检查；代码审查发现遗漏时补触发门禁，不得以实现已经完成为由跳过。

任一检查项回答“是”时，立即暂停后续规格、验收测试和生产实现，由 Agent 输出 ADR 候选并等待负责人裁决。

## 触发检查表

1. **既有决策**：是否改变、推翻或绕过任何 `accepted` ADR？
2. **系统边界**：是否改变服务职责、数据所有权、跨服务调用方向、部署拓扑或信任边界？
3. **公共契约**：是否引入或改变难以兼容的 API、事件、SSE、Evidence Contract、持久化格式或跨服务身份语义？
4. **数据与安全**：是否改变权限模型、鉴权时机、敏感信息处理、数据保留、删除、备份、恢复或审计策略？
5. **核心机制**：是否在两个以上可行方案中，为核心 Pipeline、基础设施、框架、存储引擎或关键依赖选择一个长期方案？
6. **不可逆性**：该决定是否产生高迁移成本、破坏性数据变更、外部兼容承诺，或上线后难以安全回滚？
7. **跨规范影响**：是否需要同时修改两个或更多权威规范，并且这些修改共同依赖一个需要解释的设计取舍？
8. **长期例外**：是否偏离现有架构原则、开发门禁或安全基线，并让该例外持续存在，而非短期故障处置？

第 3 项中的向后兼容字段扩展，只有形成新的长期约束时才命中。第 7 项只计算同一核心决策造成的跨规范影响，普通功能同步多处文档不自动命中。

同一核心设计取舍命中多个检查项时，只创建一份 ADR 候选和一份 ADR，并在“命中的检查项”中列出全部编号；只有彼此独立的决定才拆分为多份 ADR。

## 不触发范围

以下情况默认不创建 ADR：已有规范唯一确定实现方式；局部、可替换、低成本回滚的实现细节；不改变外部行为的重构或性能优化；不形成长期约束的向后兼容字段扩展；让实现重新符合既有规范的 Bug 修复；文案、注释、链接和格式修复；未进入生产且未形成兼容承诺的短期实验。

若同一工作同时符合排除项和触发项，以触发项为准并交由负责人裁决。

## 裁决与解除门禁

Agent 命中门禁时必须输出：

```text
ADR 候选
- 候选标题：
- 命中的检查项：
- 待决定的问题：
- 至少两个可行方案：
- 长期影响：
- 是否涉及既有 ADR：
- 建议：创建 ADR / 申请豁免
```

负责人对 Agent 的命中判断有异议时，必须明确回复 `未命中 ADR：<理由>`。相关规格必须记录 Agent 判断的命中项、负责人、裁决理由和日期；完成记录后才可按未命中路径继续。除该格式外，负责人回复含糊时保持暂停，Agent 不得自行推断。

`创建 ADR` 只选择创建路径，不解除门禁。相关 ADR 必须实际创建并完成评审，且负责人明确接受为 `accepted` 后才解除门禁；若为替代既有 ADR，还必须完成新旧状态同步和双向链接。`豁免 ADR：<理由>` 只有在相关规格记录命中项、裁决人、理由和日期后才解除门禁。“继续做”“按建议处理”、普通规格批准或实现批准均不构成 ADR 裁决。

未命中时，相关规格必须记录 `ADR 检查 1–8：否`；只写“无需 ADR”不满足审查要求。

## 替代既有 ADR

改变、推翻或绕过 `accepted` ADR 时必须创建新 ADR，不允许豁免。新 ADR 在讨论期间为 `proposed`；负责人明确接受后变为 `accepted`，旧 ADR同时变为 `superseded`。

新旧 ADR 必须建立双向链接。历史 ADR 正文不得为了符合新决定而重写；不改变语义的错别字、格式和失效链接修复不受此限制。

## 审查要求

- 规格评审没有 ADR 检查结果时，阻止进入验收测试设计。
- 代码审查发现明显命中项却没有 ADR 或豁免记录时，作为阻断问题。
- 负责人回复含糊，或 `创建 ADR` 路径的 ADR 尚未 `accepted` 时，保持暂停，Agent 不得自行推断。
- 只有正式规范定义的事故处置流程可以暂时绕过；没有这种规范时，不得以“紧急”为理由跳过门禁。
