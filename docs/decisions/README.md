# 架构决策记录

本目录记录会长期影响服务边界、安全、数据生命周期、公共契约或兼容性的决策。ADR 的标题、状态、编号和章节格式同时遵循 [文档格式规范](../guides/DOCUMENT_FORMAT.md)。

每份 ADR 使用状态 `proposed|accepted|superseded|deprecated`，包含背景、决策、后果、被否决方案、重新评估触发条件和相关规范。已接受 ADR 不因实现尚未完成而失效；发现新信息时必须先判断是修订、替代还是仅澄清实现。

## 创建门禁

每项新功能、Bug 修复、行为变更或架构调整必须在规格设计开始时执行 ADR 检查。设计过程中出现新的方案选择或影响范围扩大时重新检查；代码审查发现遗漏时补触发门禁，不得以实现已经完成为由跳过。

任一检查项回答“是”时，立即暂停后续规格、验收测试和生产实现。命中只表示必须进入 ADR 裁决，不等于自动创建新编号；Agent 必须先按“决策变更类型”判断修订、替代或澄清，再输出候选并等待负责人裁决。

## 触发检查表

1. **既有决策**：是否改变、推翻或绕过任何 `accepted` ADR？
2. **系统边界**：是否改变服务职责、数据所有权、跨服务调用方向、部署拓扑或信任边界？
3. **公共契约**：是否引入或改变难以兼容的 API、事件、SSE、Evidence Contract、持久化格式或跨服务身份语义？
4. **数据与安全**：是否改变权限模型、鉴权时机、敏感信息处理、数据保留、删除、备份、恢复或审计策略？
5. **核心机制**：是否在两个以上可行方案中，为核心 Pipeline、基础设施、框架、存储引擎或关键依赖选择一个长期方案？
6. **不可逆性**：该决定是否产生高迁移成本、破坏性数据变更、外部兼容承诺，或上线后难以安全回滚？
7. **跨规范影响**：是否需要同时修改两个或更多权威规范，并且这些修改共同依赖一个需要解释的设计取舍？
8. **长期例外**：是否偏离现有架构原则、开发门禁或安全基线，并让该例外持续存在，而非短期故障处置？

第 3 项中的向后兼容字段扩展，只有形成新的长期约束时才命中。第 7 项只计算同一核心决策造成的跨规范影响，普通功能同步多处文档不自动命中。

同一核心设计取舍命中多个检查项时，只输出一份 ADR 候选，并在“命中的检查项”中列出全部编号；只有彼此独立的决定才拆分。是否产生新 ADR 编号由下节裁决。

## 决策变更类型

命中检查项后，按以下互斥类型处理：

| 类型 | 判定 | 处理 |
|:---|:---|:---|
| 修订 | 仍属于同一决策家族，只细化局部范围、参数、顺序、职责或退出条件，核心前提和长期方向不变 | 修改原 ADR，在原文增加带日期的修订记录；不创建新编号 |
| 替代 | 推翻核心前提，改变服务边界、数据所有权、安全模型、不可逆迁移或既有兼容承诺 | 创建新 ADR；接受后将旧 ADR 标记为 `superseded`，并建立双向链接 |
| 澄清或修复 | 不改变已接受决策，只补齐规范、让实现重新符合规范或清理文档 | 不得创建 ADR；在唯一权威规范和 `docs/CHANGELOG.md` 中记录实际变化 |

无法明确归类时保持门禁，由负责人在候选中裁决，不得为规避修订审查而新建 ADR，也不得为减少文件数量而把替代伪装成修订。

## 不触发范围

以下情况默认不创建 ADR：已有规范唯一确定实现方式；局部、可替换、低成本回滚的实现细节；不改变外部行为的重构或性能优化；不形成长期约束的向后兼容字段扩展；让实现重新符合既有规范的 Bug 修复；文案、注释、链接和格式修复；未进入生产且未形成兼容承诺的短期实验。

若同一工作同时符合排除项和触发项，以触发项为准并交由负责人裁决。

## 裁决与解除门禁

Agent 命中门禁时必须输出：

```text
ADR 候选
- 候选标题：
- 命中的检查项：
- 待决定的问题：
- 至少两个可行方案：
- 长期影响：
- 是否涉及既有 ADR：
- 建议：创建 ADR / 申请豁免
```

负责人对 Agent 的命中判断有异议时，必须明确回复 `未命中 ADR：<理由>`。命中项、负责人、裁决理由和日期必须按下文「记录位置」完整记录；完成记录后才可按未命中路径继续。除该格式外，负责人回复含糊时保持暂停，Agent 不得自行推断。

`创建 ADR` 只选择替代或全新决策路径，不解除门禁。相关 ADR 必须实际创建并完成评审，且负责人明确接受为 `accepted` 后才解除门禁；若为替代既有 ADR，还必须完成新旧状态同步和双向链接。`修订 ADR-NNN：<理由>` 只有在原 ADR 完成修订记录、相关规范同步且负责人确认后才解除门禁。`豁免 ADR：<理由>` 只有在相关规范或 CHANGELOG 当次条目记录命中项、裁决人、理由和日期后才解除门禁（记录位置见下）。“继续做”“按建议处理”、普通规格批准或实现批准均不构成 ADR 裁决。

未命中时，必须记录 `ADR 检查 1–8：否`；只写“无需 ADR”不满足审查要求。

**记录位置**：ADR 检查命中项、负责人、裁决理由和日期可以二选一记录——直接写在相关规范，或集中写入 `docs/CHANGELOG.md` 的当次变更条目；采用后者时相关规范必须保留 `ADR 检查 1–8：否（记录见 CHANGELOG，YYYY-MM-DD）` 指针。无论采用哪种位置，命中项、负责人、裁决理由和日期都必须完整记录，不得只留下“否”而无记录。同一裁决只在一个位置定义，其他文档使用链接引用。

## 替代或修订既有 ADR

推翻或绕过 `accepted` ADR 的核心决策时必须创建新 ADR，不允许豁免。新 ADR 在讨论期间为 `proposed`；负责人明确接受后变为 `accepted`，旧 ADR 同时变为 `superseded`。

新旧 ADR 必须建立双向链接。历史 ADR 正文不得为了符合新决定而重写；不改变语义的错别字、格式和失效链接修复不受此限制。

仍属同一决策家族的局部细化必须修订原 ADR：正文更新当前有效决策，并新增包含日期、变更点、理由、影响范围和负责人裁决的“修订记录”。修订不能抹除原始背景、备选方案和历史理由；若无法同时保留历史可解释性和当前有效表述，应改走替代路径。

## 审查要求

- 规格评审没有 ADR 检查结果时，阻止进入验收测试设计。
- 代码审查发现明显命中项却没有 ADR 或豁免记录时，作为阻断问题。
- 负责人回复含糊，或 `创建 ADR` 路径的 ADR 尚未 `accepted` 时，保持暂停，Agent 不得自行推断。
- 只有正式规范定义的事故处置流程可以暂时绕过；没有这种规范时，不得以“紧急”为理由跳过门禁。

## 治理 smoke

ADR 或本索引发生变化时，必须执行：

```bash
bash scripts/check-adr-governance.sh
bash scripts/check-document-format.sh
git diff --check
```

检查必须确认当前与历史索引互斥、索引链接存在、ADR 状态与所在索引一致，以及 `AGENTS.md` 与 `CLAUDE.md` 逐字节一致。
