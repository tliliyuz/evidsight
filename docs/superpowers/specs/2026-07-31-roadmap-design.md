# EvidSight ROADMAP 文档设计

## 1. 目标

为据见（EvidSight）建立不绑定具体日期的产品级实施路线图。路线图把 PRD v1.0 范围、总体架构、Monorepo 迁移和后续专项规范组织为可执行的阶段顺序，并为每个阶段定义明确的进入条件、交付物和退出门禁。

路线图用于回答“先做什么、依赖什么、达到什么条件才能进入下一阶段”，不替代专项设计或任务级实施计划。

## 2. 文档定位与权威边界

- `docs/PRD.md`：产品定位、用户、功能范围和成功指标的权威来源。
- `docs/ARCHITECTURE.md`：系统边界、部署拓扑和系统级约束的权威来源。
- `docs/MONOREPO_MIGRATION_PLAN.md`：第一阶段代码布局迁移步骤的权威来源。
- `docs/ROADMAP.md`：阶段顺序、阶段目标、依赖关系和发布门禁的权威来源。
- API、Contract、Database、Pipeline、Frontend 和 UI 专项规范：各自字段、状态机、算法与交互细节的权威来源。

ROADMAP 只引用上述细节，不复制定义，避免多份规范漂移。

## 3. 编排方案

采用“阶段里程碑 + 验收门禁”，不写具体日期、周数或工期。每个里程碑使用相同结构：

1. 阶段目标；
2. 进入条件；
3. 范围内工作；
4. 必须完成的规范；
5. 主要交付物；
6. 退出门禁；
7. 明确不在本阶段处理的内容。

任务级命令、文件列表和逐步实施动作留在对应实施计划中。路线图不维护与实施计划重复的复选框清单。

## 4. 里程碑结构

### M0：规范基线与 Monorepo 迁移

以已确认的 PRD、总体架构和迁移计划为输入，完成来源基线冻结、历史导入、目录整形、独立构建边界、Compose 骨架和跨仓库验证。退出时形成可独立测试的 Knowledge Service、Research Service 和统一 Web 基线，但不宣称 v1.0 已可发布。

### M1：统一身份、权限和基础契约

完成统一 JWT、用户禁用语义、服务间认证、知识库和研究任务权限矩阵，以及跨服务错误与版本规则。先完成 API 和 Contract 规范及契约测试，再允许跨服务业务实现。

### M2：Knowledge Service 稳定化与 Internal Retrieval

在迁入后的 Knowledge Service 中完成行为等价验证、权限感知的内部检索接口、内部 Evidence 输出、文档位置回溯及 Provider 契约测试。退出时 Research Service 可以只通过稳定契约消费企业知识，不接触 Knowledge 数据库、向量目录或业务模型。

### M3：Research Service 接入内部知识

把 Knowledge Search Tool 接入研究 Pipeline，完成 `knowledge`、`web`、`hybrid` 三种来源策略、内外证据融合、隐私边界、任务取消与恢复。退出门禁覆盖三类来源的端到端研究流程，并验证内部资料不会自动进入互联网搜索词。

### M4：统一 Web、报告与证据联动

整合统一导航、问答、研究创建、运行状态、历史、报告阅读和 Evidence 面板。完成报告引用与证据双向联动、内部证据实时权限复核，以及 Chat SSE 与 Research SSE 的独立状态机。

### M5：治理、可观察性和部署验收

完成用户、内容、任务的基础治理，补齐审计、成本、日志、指标、Trace、备份恢复和受控降级。按 2 vCPU / 2 GB RAM 基线验证 Compose 部署、资源上限、队列背压和恢复演练。

### M6：v1.0 发布门禁与后续演进

执行 PRD 的端到端验收场景和成功指标检查，完成安全、迁移、回滚、文档一致性和回归测试门禁。v1.0 通过后，P1 按独立规格进入后续版本；P2 只保留方向，不提前设计实现。

## 5. 依赖关系

总体主线为 `M0 → M1 → M2 → M3 → M4 → M5 → M6`。

- 专项规范可以在其前置里程碑后期提前编写，但生产实现必须等待相关规范和验收测试通过。
- M2 的 Knowledge 稳定化工作可与 M1 的非契约部分并行，但 Internal Retrieval 实现必须等待统一身份和基础 Contract 确认。
- M4 的静态视觉与信息架构设计可提前开展，但真实联调依赖 M2、M3 的 API、SSE 和 Evidence Contract。
- M5 的日志、指标和资源测试应在早期阶段持续接入，M5 负责形成完整发布门禁，不代表此前可以忽略可观察性。

## 6. 状态与变更规则

里程碑状态统一使用：`未开始`、`进行中`、`受阻`、`已完成`。

- 只有退出门禁全部满足，里程碑才能标记为“已完成”。
- “受阻”必须记录阻塞条件和解除条件，不使用模糊百分比代替事实。
- ROADMAP 状态变化同步写入 `docs/CHANGELOG.md`；范围或架构发生变化时，先更新对应权威规范，必要时新增 ADR，再调整 ROADMAP。
- 不在 ROADMAP 中记录未经实际验证的 PASS、完成率或发布日期承诺。

## 7. ROADMAP 正文建议结构

1. 文档元数据与使用说明；
2. 范围、原则和权威边界；
3. 里程碑总览；
4. M0—M6 逐阶段定义；
5. 跨阶段依赖与可并行工作；
6. v1.0 发布总门禁；
7. v1.x（P1）和远期（P2）演进；
8. 路线图维护规则；
9. 相关文档。

## 8. 成功标准

- PRD 的全部 P0 能力都能映射到且只映射到一个主要交付里程碑。
- 每个里程碑都有可观察的进入条件、交付物和退出门禁。
- 路线图不包含具体日期、虚构工期或未经验证的完成状态。
- 路线图与 PRD、总体架构和迁移计划不存在范围或顺序冲突。
- API、字段、状态机、算法和 UI Token 等专项事实通过链接引用，不在路线图中重复定义。
- P1 与 P2 和 v1.0 发布门禁明确分离，避免范围蔓延。
