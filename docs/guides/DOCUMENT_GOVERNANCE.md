# DOCUMENT GOVERNANCE — 文档治理指南

| 属性 | 值 |
|:---|:---|
| 文档状态 | 已确认治理基线 |
| 最后更新 | 2026-08-03 |

本文定义 EvidSight 如何发现、归属、裁决、固化和验证产品与工程事实。它负责回答“一个事实应进入哪份文档、实现与规范冲突时怎么办”；重要架构取舍是否需要 ADR，仍由 [ADR 治理规则](../decisions/README.md) 唯一裁决。

ADR 检查 1–8：否。本指南只补充既有 SDD 的文档取证与裁决流程，不改变产品行为、服务边界、公共契约、数据与安全策略或技术机制。

## 1. 治理目标

- 规范是实现输入，不是对既有代码的追认记录。
- 同一事实只有一个权威来源，其他文档只引用或记录状态。
- 明确区分当前实现、已批准目标、迁移过程和验证结果。
- 测试只能执行规范，不得凭自身存在为未授权行为取得合法性。
- 任何例外都有负责人、理由、期限和退出条件，不形成无期限兼容债务。

本文不定义具体产品行为、接口字段、数据库结构或 Pipeline 算法。

## 2. 文档类型与职责

| 类型 | 回答的问题 | 权威入口 | 不得承担 |
|:---|:---|:---|:---|
| 产品规范 | 做什么、为谁做、如何验收 | `docs/specs/PRD.md` | 技术实现步骤 |
| 架构规范 | 服务边界、部署拓扑、依赖方向 | `docs/specs/ARCHITECTURE.md` | 重要取舍的讨论历史 |
| 专项规范 | 身份、API、配置、测试、数据与运行规则 | `docs/specs/` 对应文档 | 重复其他专项事实 |
| 跨服务契约 | 服务间数据 Schema、版本和 Fixture | `packages/contracts/` | HTTP 认证载体或服务内部模型 |
| 模块规范 | 模块数据库、Pipeline、前端行为与视觉 | 模块 `docs/` | 跨模块系统事实 |
| ADR | 为什么选择一项长期架构方案 | `docs/decisions/` | 代替当前有效规范 |
| 计划 | 何时、按什么依赖顺序交付 | `docs/plans/` | 宣称能力已经实现 |
| 指南 | 如何执行开发、治理和运维动作 | `docs/guides/` | 定义产品行为 |
| Changelog | 已发生的可审查变化、实施验证结果、ADR 检查/裁决与迁移态记录 | `docs/CHANGELOG.md` | 未来计划、未运行结果 |

完整主题归属以根目录 `AGENTS.md` 的权威文档矩阵为准。

## 3. 事实状态模型

每项需要跨文档跟踪的行为只能处于以下状态之一：

| 状态 | 判定条件 | 可以声称 |
|:---|:---|:---|
| `observed` | 已从代码、运行结果或旧文档取证，尚未裁决 | “当前观察到” |
| `proposed` | 已提出可审查方案，尚未获负责人确认 | “建议” |
| `specified` | 权威规范已获确认，可导出明确验收条件 | “已批准规范” |
| `implemented` | 实现已完成，但尚未完成要求的完整验证 | “已实现，待验证” |
| `verified` | 规范要求的测试和发布门禁均有本次实际证据 | “已验证” |
| `deprecated` | 已提供替代方案、观测窗口和退出条件 | “已弃用，兼容中” |
| `retired` | Consumer 已退出，兼容入口或旧格式已移除 | “已移除” |

不得把“文档状态为已确认设计”解释为对应功能已经实现；不得把旧测试通过解释为其断言行为已获规范授权。

## 4. 文档治理门禁

新功能、Bug 修复、行为变更、兼容处理以及发现实现与规范不一致时，按以下顺序执行：

```text
事实取证
  → 确定唯一权威来源
  → 冲突分类
  → ADR 检查与裁决
  → 文档裁决
  → 更新权威规范
  → 导出验收条件与测试
  → RED / GREEN / REFACTOR
  → 验证规范与实现一致
  → 更新 Changelog 与里程碑状态
```

门禁规则：

1. 取证前不提出修复方案；至少检查权威规范、当前实现、相关测试和最近相关提交。
2. 权威来源缺失或两份权威文档定义同一事实时，暂停测试与实现。
3. ADR 检查必须先于规格裁决；命中项按 ADR 治理规则解除门禁。
4. 实现与已确认规范冲突时，默认修正实现；修改规范需要独立理由和负责人明确批准。
5. 负责人未明确选择“实现服从规范”或“规范变更”前，不得用测试固化任一方案。
6. 迁移期例外必须同时写明当前态、目标态、兼容范围、Consumer、观测方式、截止条件和删除动作。
7. 完成声明必须分别说明规范、实现和验证状态，不能使用一个“完成”覆盖三者。

## 5. 冲突分类与处理

### 5.1 实现偏离规范

判定：权威规范已经唯一、明确地定义行为，代码或测试与其不同。

处理：将其作为缺陷处理，规范保持不变；从规范导出正确验收测试，观察 RED 后修正实现。只有业务目标本身需要改变时，才走“规范变更”路径并重新执行 ADR 检查。

### 5.2 实现领先、规范缺失

判定：实现或测试已经形成外部可观察行为，但权威规范没有定义。

处理：标记为 `observed` 并暂停继续扩展。负责人必须在以下两项中裁决：

- 删除或收敛该行为，使实现回到已有规范；
- 正式采纳该行为，先完成 ADR 检查和规范评审，再重写从规范导出的测试。

不得仅因代码已存在、用户可能使用或测试已通过而选择正式采纳。

### 5.3 迁移态与目标态不同

判定：当前实现为了兼容旧 Consumer 暂时保留旧字段、路由、主键或行为，而已批准规范定义了最终状态。

处理：以下六项必须完整记录——当前真实 Schema 或接口、最终目标、迁移步骤与先后依赖、Consumer 清单、兼容调用量或等价观测、退出门禁和删除时点。记录位置二选一：

- 直接在权威规范中记录（适用于迁移面窄、六项较短的场景）；
- 集中写入 `docs/CHANGELOG.md` 的当次变更条目，权威规范只保留一句话的当前态声明与指向该条目的链接（`（迁移态，记录见 CHANGELOG，YYYY-MM-DD）`）。

同一迁移事实只在一个记录位置定义，其他文档使用链接引用。缺少任一项时，不得把偏差称为“迁移期兼容”。

### 5.4 权威文档冲突

判定：两份文档对同一事实给出不同定义。

处理：按 `AGENTS.md` 权威矩阵确定唯一归属。归属文档保留定义，其他文档删除重复描述并改为链接；若矩阵本身不能裁决，先由负责人确认归属。不得选择更方便当前实现的一方。

## 6. 文档裁决候选

每个待裁决问题使用以下格式，且一次只处理一个逻辑事实：

```text
文档裁决候选
- 候选标题：
- 发现日期：YYYY-MM-DD
- 当前实现事实：
- 当前测试事实：
- 唯一权威来源：
- 冲突类型：实现偏离 / 实现领先 / 迁移态 / 文档冲突
- 当前态：
- 已批准目标态：
- 可行方案：至少两个；若规范已唯一确定，可写“实现服从规范”与“申请变更规范”
- ADR 检查结果：按 docs/decisions/README.md 记录
- 建议裁决：
- 受影响文档、测试与实现：
- 迁移和退出条件：不适用时写“不适用”
- 负责人裁决：待确认
```

有效裁决必须明确回复以下一种：

- `实现服从规范：<理由>`；
- `批准规范变更：<方案与理由>`；
- ADR 治理规则要求的 `创建 ADR`、`豁免 ADR：<理由>` 或 `未命中 ADR：<理由>`。

“继续”“可以”“按建议处理”等普通实施授权不能替代存在规范冲突时的文档裁决。

## 7. 规范变更方法

规范变更必须满足：

1. 在唯一权威来源中定义行为、边界、失败语义和验收条件。
2. 其他文档只更新引用、局部投影或实施状态，不复制完整定义。
3. 公共 API、Contract、持久化格式和配置键同步更新其专属权威资产。
4. `docs/specs/TESTING.md` 只记录从规范导出的验收矩阵，不记录未经运行的 PASS。
5. `docs/CHANGELOG.md` 记录实际发生的规范或行为变化，并标注实际日期。
6. 纯文档变更执行格式、链接、Schema 或架构 smoke；涉及业务行为的后续实现仍完整执行 SDD。

## 8. 测试与实现的反向审计

每个里程碑开始、退出和重大身份/权限切片完成后执行一次反向审计：

1. 从测试断言提取外部可观察行为。
2. 为每项行为定位唯一权威规范段落。
3. 无规范映射的测试标记为“实现领先”，不得作为回归基线继续扩展。
4. 与规范相反的测试标记为“实现偏离”，先观察正确 RED 再替换旧断言。
5. 文档声明已实现但没有测试或运行证据的项目降回 `specified` 或 `implemented`。
6. 将未关闭项写入当前里程碑的可审查清单；不在 Changelog 中伪装为已完成。

审计最少输出：事实、证据路径、权威来源、冲突类型、建议裁决和阻塞的里程碑门禁。

## 9. 评审检查表

文档评审必须确认：

- [ ] 同一事实只有一个权威来源；
- [ ] ADR 检查结果满足治理规则；
- [ ] 当前态、目标态和实现状态没有混写；
- [ ] 迁移例外包含 Consumer、观测和退出条件；
- [ ] API、Contract、数据库、前端和配置的局部投影与权威来源一致；
- [ ] 验收条件可以直接转化为自动化测试；
- [ ] Changelog 只记录实际发生的变化并包含日期；
- [ ] 没有 `TBD`、`TODO`、无期限“临时”或无法验证的描述；
- [ ] 链接、标题、Schema 引用和版本号可解析；
- [ ] 实现与测试没有被当作规范来源。

任一项不满足时，文档评审不得通过，后续测试或生产实现保持暂停。
